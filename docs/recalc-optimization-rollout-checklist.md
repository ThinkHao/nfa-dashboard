# 复算性能优化上线/回滚检查清单

## 上线前检查

1. 确认代码版本包含以下改动：
- 复算分批提交（500 条/批）与任务进度实时更新
- 复算缓存优化（existing map、费率缓存、折损规则缓存）
- 新迁移：`sql/migrations/034_add-settlement-customer-composite-index.sql`

2. 执行 SQL 迁移守卫检查：
```bash
python scripts/sql_migration_guard.py check
```

3. 数据库容量与锁风险评估（建议）：
- 检查 `settlement_customer`、`nfa_school_settlement` 表大小与峰值负载时段
- 选择低峰时段执行索引变更

4. 预估任务对比基线：
- 记录当前复算吞吐（条/秒）与总耗时
- 记录任务进度接口刷新表现（`processed_count/total_count`）

## 上线执行步骤

1. 先执行迁移 `034`（补索引）
2. 部署后端新版本
3. 触发同口径复算任务（建议 1~3 天样本 + 一段完整月样本）
4. 观察任务详情：
- `total_count` 在 running 后已写入
- `processed_count` 每批（500）递增
- 任务最终转为 `success`

## 上线后验证

1. 功能正确性：
- 对比优化前后同区间复算结果（金额、费率、归属）无口径变化

2. 性能指标：
- 复算总时长下降
- 数据库慢查询数量下降（尤其复算窗口）

3. 稳定性：
- 无异常失败任务堆积
- 后端日志无新增 panic/fatal

## 回滚策略

1. 应用回滚：
- 若发现功能异常，优先回滚后端应用版本（数据库索引可保留）

2. 任务处置：
- 运行中任务若需中止，先评估业务窗口，避免重复触发造成资源争用

3. 索引回滚（仅必要时）：
- 若确认新增索引引发明显副作用，再执行 `DROP INDEX`
- 建议在低峰时段进行，并提前评估影响

## 紧急排查要点

1. 任务看似“卡住”时优先看：
- 后端日志是否持续出现复算 UPDATE/UPSERT
- `processed_count` 是否持续增长

2. 若 `processed_count` 不增长：
- 检查任务状态是否被置为 `failed`
- 检查数据库连接与锁等待
- 检查是否触发了异常回滚
